**진행 순서**
1. **사용 환경부터 보호합니다.** 개인 OS 계정, 화면 잠금, 디스크 암호화를 사용하고 보관함·백업의 공유 권한을 확인합니다. 디스크 암호화는 분실 대응용이며, 이미 로그인된 PC의 악성 프로그램까지 막지는 못합니다.
2. **앱의 비밀정보 저장을 먼저 개선합니다.** 현재 파일에 저장되는 API 키·SFTP 인증 정보·로그인 유지 토큰을 OS 보안 저장소로 옮깁니다. 노트 저장 구조를 바꾸지 않고도 보호 효과가 있는 작업입니다.
3. **단일 사용자에 맞게 인증을 정리합니다.** 관리자·일반 사용자 구분을 걷어내고, 앱 잠금이 필요한지만 선택하게 합니다. 이때 기존 인증 검사를 무작정 삭제하기보다는 단일 사용자 모드의 접근 정책으로 정리해야 합니다.
4. **민감한 자료가 있다면 백업 암호화부터 검토합니다.** 비공개 Git 저장소나 SFTP도 저장된 내용을 앱 비밀번호로 암호화해 주지는 않습니다. 원격 저장소 운영자에게도 내용을 숨겨야 한다면 업로드 전에 암호화해야 합니다.

보관함 전체 암호화는 **“노트 파일이나 백업을 누군가 가져가도 읽을 수 없어야 한다”**는 요구가 있을 때 진행하면 됩니다. 키 분실 시 복구, 첨부파일, 기존 평문 백업·Git 이력까지 함께 다뤄야 해서 단순히 저장 함수에 암호화를 추가하는 작업은 아닙니다.

**이 프로젝트에서는 우선 `Markdown 유지 → 비밀정보의 OS 보안 저장 → 단일 사용자 모드로 단순화`까지 진행하는 쪽이 적절합니다.** 주민번호·금융정보·회사 기밀 같은 자료를 넣을 예정이라면, 그때는 순서를 바꿔 보관함과 백업 암호화를 먼저 설계하는 게 맞습니다.
